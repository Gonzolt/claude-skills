# Automation security

`setup_automation.sh` schedules only `python3 scripts/daily.py`. The collector never invokes Claude Code, Codex, a shell, plugins, or code from a paper. It performs fixed HTTPS GET requests to `export.arxiv.org/api/query` and `api.crossref.org/works`, parses metadata, applies local preferences, and writes SQLite/Markdown under `JUNSHI_HOME`. It does not read the papers folder or profile, send private memory to a model, or generate speculative ideas. Only configured arXiv queries and journal ISSNs are transmitted to metadata providers; do not put confidential research details in queries.

Requests have timeouts, bounded retries and response sizes; redirects and arbitrary endpoint URLs are rejected. Remote metadata is escaped in generated Markdown. Files created by CLI/cron use a private umask. A process lock prevents overlapping collectors, database transactions serialize state changes, same-day publication is idempotent, and a failed source aborts publication with a nonzero exit and log message. Narrow sources when a digest reports caps. Check the cron log after initial setup and after changing sources; errors are logged, not pushed as notifications.

This is an application-level execution boundary, not an OS sandbox: the trusted Python process runs with the scheduling user's account permissions. Keep the installed code and data directory writable only by that user, review updates, and use a dedicated OS account or container if stronger isolation is required. Do not schedule from an untrusted/shared checkout. The machine must be awake with network access; cron does not recover jobs missed during sleep. Use the machine's timezone for scheduling and digest filenames. Rotate `cron-junshi.log` as needed.

For richer research ideas, use an interactive host with normal permission controls. Treat retrieved papers and stored excerpts as untrusted data, not executable instructions. Host providers receive whatever context the interactive agent uses, under that host's data policy. Review unpublished/confidential material before supplying it.

The setup script validates inputs, shows the exact cron entry, and asks before installing or replacing matching Junshi lines. Old permission-bypass jobs are not safe merely because the skill was updated: run setup to replace them, or remove them with `crontab -e`. Review any other cron line containing `research-junshi` before accepting replacement. The repo does not change global host permissions or schedule anything during installation/tests.
